## Problem & user

RocketShip PMs need this handled: Juno is an AI assistant for product managers that helps track requests from different teams and clients across company channels, consolidate related requests into a single task, and prioritize them using our methodology.. Juno does this inside limits a human set on purpose, and defends every call it makes.

## 01 Context · Data Requirements

**Required sources, and exclusions**

Juno gets context in four ways, depending on the source:

In the prompt (small, stable, needed on every run)
- Juno's role, task and constraints (skill file)
- The R × S × B scoring model, thresholds and override rule
- The approved development task template
- Product Strategy and Roadmap summary (if it grows too large, moves to retrieval)

Fetched on demand (fresh data, only what the current signal needs)
- New signals from Slack, Jira, Notion, email and call notes in the CRM — read-only
- Client data from the CRM for the client behind each signal: ARR, contract renewal date and churn signals, used to calculate Business Risk (B)

Retrieved and injected (RAG) (large and growing set)
- Existing tasks in Juno's dashboard: for every new signal, Juno retrieves the most similar existing tasks to decide whether to link the signal to one of them or create a new task

Not loaded in full
- Whole channel histories are never loaded into context: too large and too expensive on every run

**How fresh must it be**

Changes in sources appear in Juno’s dashboard on the next Juno run. Juno runs every 2 hours from 8 am to 8 pm.
If a source is unreachable, Juno still runs on the available data and marks the missing fields as “no data” instead of guessing.

## 02 Tools · System Capabilities

**The verb list**

Slack, Jira, Notion, email, and call notes in the CRM - Read;
Requests data about each client from the CRM - Read;
Consolidates into a task, edits existing tasks in its dashboard - Write; 
Write development tasks based on template - Write; 
Compare new incoming signals against existing tasks - Read; 
Sets and updates the R × S × B score and priority of tasks in its dashboard - Write;

**Deliberate omissions**

- No write access to Jira: Juno does not create, edit or assign Jira tickets. The PM copies the development task into Jira manually, so a person decides what goes into development;
- No send capability: Juno does not reply to clients or post in Slack/email. Communication with clients stays with people;
- No write access to the CRM: Juno only reads client data and never changes it;
- No web access: Juno has no internet search or browsing tool, so it relies only on data from the company’s internal systems and cannot pull in unverified external information;

## 04 Memory · Data Requirements

**What persists, at what scope**

Juno keeps all tasks, their linked signals and scores so that when a similar request comes in, it does not create a duplicate task. All information is visible to the whole team; nothing is restricted between users.

**Expiry and write rules**

Tasks are stored forever, including closed ones, so new signals can always be compared with past tasks. If a new signal matches a closed task, Juno links the signal to it and flags the task “New signal on a closed task — needs PM review”. The PM decides whether to reopen it or create a new task.
Client data has different lifetimes: company name, ARR and contract renewal date are stored and refreshed only when the client’s contract changes in the CRM. Churn signals are checked on every run, because they can appear any day. Days until renewal are recalculated from the stored date on every run.

Write rules: a human always outranks Juno. The PM can raise or lower a task’s priority; Juno keeps the PM’s value (labeled “adjusted by PM”) and never overwrites it on the next run. Only the PM decides which tasks go to Jira.

## 06 Verification · AI Testing & Measurement

**The check before output ships**

Every task created must include:

- A clearly defined score, with an explanation of why it was assigned.
- A development task description written using the specified template.
- Links to the specific sources that informed its creation.
- Alignment with the Product Roadmap and Product Strategy, both in its scope and prioritization.

**Failure behaviour**

If a task fails any check, Juno does not drop it and does not present it as final. The task is moved to a separate PM Review stage (alongside Fix now, Plan next and Backlog) with the reason shown: e.g. “missing source link”, “score explanation missing”, “development task does not match the template”, “possible conflict with the Product Strategy”. Missing data is marked “no data” instead of guessed. The PM verifies the task and moves it to the right stage. The same PM Review stage is used for new signals on closed tasks and uncertain duplicates.
