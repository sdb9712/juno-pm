## What Juno Is Doing

Risk flagging by problem prioritization gathered from Slack, Jira, Mail, Notion and CRM

## Four Levers

**Stop Conditions** (Loop):

max_steps: 3 per task, Abort: if any of the 4 verification checks still fails after step 3, Juno stops and flags the task for PM Review. If a data source fails 2x in a row, Juno stops calling it and marks its fields “no data”.
Hard timeout: 1 hour wall clock per run.

**Structured Tool Outputs** (Tools):

1) Read of Slack, Jira, Notion, email, and call notes in the CRM returns the list of problems and bugs that our clients experienced. In success scenario the status is "ok" and the list of problems provided. 
If the source responded but there are no new problems - its still valid and get the status "ok" with a "0" instead of the list of problems.  
If the source does not respond or returns an error → status “failed”. 

2) Read client data from the CRM: returns status “OK” if the CRM responded, “Failed” if it did not respond or returned an error. Every field is always returned: ARR, contract renewal date, churn signals, client name, logo. If a value is missing in the CRM, the field comes back as “no data”.

3) Write consolidations into a task / edit existing tasks in its dashboard: returns the task ID, the action (“created” or “updated”) and the number of issues linked to the task.
OK — the action is “created” and the number of linked issues is not 0, or the action is “updated” and the number of linked issues is greater than before.
No change — the action is “updated” and the number of linked issues is not greater than before.
Failed — the number of linked issues is 0 or the request is unsuccessful.
 
4) Write development task based on template: returns the task ID, the action (“created” or “updated”), the number of template sections filled out of 8 (missing sections listed by name) and a status.
OK — the action is “created”, the text is not blank and all 8 sections are filled; or the action is “updated”, the text has changed and all 8 sections are filled.
No change — the action is “updated” but the text did not change.
Failed — the text is blank, fewer than 8 sections are filled, or the request is unsuccessful.

5) Compare new incoming signals against existing tasks (read): returns a status, a match result and, if a match is found, the ID of the existing task and whether it is open or closed.
Match results: “new” — no existing task covers this issue; “match” — an existing task covers it (the signal will be linked to it and the task enriched with new details); “uncertain” — a similar task exists but it is not clear it is the same issue.
OK — the search ran and returned any of the three results.
Failed — the search did not respond or returned an error.

6) Set and update the R × S × B score and priority of tasks in its dashboard (write): returns the task ID, the values of R, S and B, the score, the priority level (Fix now / Plan next / Backlog), whether the override rule applied, who set the values (“Juno” or “adjusted by PM”) and whether a score explanation is attached.
OK — the score was written, equals R × S × B, the priority level matches the thresholds and the override rule, and the explanation is attached.
No change — the score was recalculated and is the same as before (e.g. a new signal did not change R, S or B).
Kept PM value — the PM has adjusted R, S or B for this task, so Juno did not overwrite it; the value stays labeled “adjusted by PM”.
Failed — the write did not go through, the score does not equal R × S × B, the level does not match the thresholds, or the explanation is missing.

**Confidence Thresholds** (Verification):

High confidence — none of the conditions below fired. Juno creates or updates the task and sets its priority (Fix now / Plan next / Backlog) on its own.

Medium / low confidence — any of these conditions fired. Juno still creates the task but does not set a final priority: the task goes to the PM Review stage with the condition shown as the reason.

Score cannot be built — R, S or B is missing (“no data” from the CRM) or tool 6 returns “Failed”.
Similar but different complaints — linked complaints look alike but differ in context and details, so the task becomes too broad (includes tool 5 returning “uncertain”).
Task does not fit the template — tool 4 returns fewer than 8 of 8 sections filled.
Sources disagree — signals about the same problem from different channels contradict each other (e.g. different Severity).
No source signal — the task has no link to an original signal.

Too unsure to act — not used: Juno never drops a task silently; every uncertain case goes to PM Review.

**North Star** (Context):

Merge similar bugs and improvement requests into single tasks and prioritize them by business impact (R × S × B), so the PM knows what to fix first.
Always: link every task to its source signals and explain its score.
Never: make up an issue, a client or client data that is not in the sources.

## Rules of Engagement

**Agency Permission:**

Decides alone: creates and consolidates tasks, writes development tasks, sets the R × S × B score and priority — only inside its own dashboard.
Proposes and waits: anything that goes to Jira (only the PM moves tasks there); tasks where any confidence condition fired (Lever 3) wait in PM Review without a final priority.

**Access Control:**

Juno runs under its own service account with the same visibility as the PM: it sees only what the PM can see in Slack, Jira, Notion, email and the CRM, and has read-only access to all of them. It can write only to its own dashboard. Out of reach: writing to Jira or the CRM, sending messages, and web access. Every action is logged under Juno’s account, so any action it was not allowed to take (e.g. a task appearing in Jira) is traceable to Juno.

**Fallback Protocols:**

A data source fails 2x in a row → Juno stops calling it, continues on the available data and marks its fields “no data”.
A task still fails verification after 3 steps → the task goes to PM Review with the failed check shown.
A write returns “No change” (tools 3 and 4) → Juno retries once; a second “No change” sends the task to PM Review with the reason.
The 1-hour timeout is reached → unprocessed signals are carried over to the next run.

**Checkpoints:**

A PM must review before Juno continues when:

any confidence condition fired (Lever 3);
a new signal matches a closed task;
tool 5 returns “uncertain”;
a task is about to move to Jira — only the PM does this.
